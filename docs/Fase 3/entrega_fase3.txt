AVALIAÇÃO DA ENTREGA - FASE 3
Projeto: SIAES / Oficina Mecânica
Data da análise: 2026-11-02

CONCLUSÃO EXECUTIVA
====================

A entrega atende estruturalmente a boa parte dos requisitos técnicos da Fase 3,
principalmente pela existência de quatro repositórios públicos, código de
autenticação serverless, Terraform para AWS, PostgreSQL gerenciado, cluster
EKS/HPA, pipelines GitHub Actions e documentação arquitetural.

Entretanto, não é possível afirmar que todos os requisitos estejam entregues
de forma comprovadamente funcional. Os principais pontos pendentes ou
incompletos são:

1. A pipeline do repositório principal não executa um deploy real: o passo de
   deploy apenas imprime mensagens e gera os manifestos Kustomize.
2. O HPA versionado no repositório principal escala de 2 a 10 réplicas, embora
   a documentação e alguns requisitos declarados indiquem 2 a 5.
3. O Datadog está desabilitado por padrão no arquivo de variáveis do
   repositório Kubernetes (`enable_datadog = false`), portanto a observabilidade
   de negócio não fica ativa apenas com a configuração fornecida.
4. O RDS está com `multi_az = false` no exemplo de configuração. Alta
   disponibilidade Multi-AZ é descrita, mas não é o comportamento padrão.
5. A Lambda é publicada com runtime Terraform `dotnet8`, apesar de o código e
   a documentação indicarem .NET 10. Além disso, o Terraform referencia um ZIP
   dummy, enquanto a pipeline gera outro arquivo (`lambda_payload.zip`).
6. A consulta da Lambda não lê um campo de status do cliente; ela atribui
   `Status = "Ativo"` depois da consulta. Assim, a existência é consultada,
   mas o status real não é validado.
7. Não foram localizados no material analisado o vídeo de demonstração, o PDF
   único para o Portal do Aluno, links comprovadamente ativos de deploy ou
   evidência verificável da proteção de branches e da inclusão do usuário
   `soat-architecture`.

Classificação utilizada:
ATENDE     - há implementação/evidência consistente no código ou IaC.
PARCIAL    - existe implementação ou documentação, mas há lacunas,
             configuração desabilitada, divergência ou ausência de prova.
NÃO COMPROVADO - o item pode ser alegado no README, porém não há evidência
                 verificável no material consultado.
NÃO ATENDE - há evidência de que o requisito não está implementado.


1. AUTENTICAÇÃO E API GATEWAY
================================

1.1 Implementar um API Gateway
Status: ATENDE PARCIALMENTE

Há implementação Terraform de AWS API Gateway HTTP API v2 no repositório
`FIAP.Tech.Challenge.Lambda`, com integração AWS_PROXY, payload 2.0 e rotas
`POST /auth/token` e `POST /auth/login` (`infra/main.tf`).

Também há um API Gateway central no repositório
`FIAP.Tech.Challenge.Infra.Kubernetes`, com CORS, logs de acesso JSON no
CloudWatch e VPC Link (`api_gateway.tf`). A arquitetura e o roteamento estão
documentados.

A classificação é parcial porque os dois gateways são descritos como parte da
arquitetura, mas não foi localizada uma configuração completa que conecte as
rotas `/api/*` do gateway central ao serviço real do EKS/ALB. Também não há
evidência de endpoint público ativo ou de execução bem-sucedida do deploy.

1.2 Proteger rotas sensíveis com autenticação via CPF
Status: ATENDE

A aplicação Lambda recebe CPF em JSON, aceita CPF com máscara ou somente
dígitos, valida os dígitos verificadores pelo algoritmo Módulo 11 e emite
claims compatíveis com a API principal. A API principal configura JWT Bearer e
protege controllers por `[Authorize]` e por roles.

Evidências:
- `FIAP.Tech.Challenge.Lambda/src/FIAP.Tech.Challenge.Lambda/Function.cs`;
- `FIAP.Tech.Challenge.Lambda/src/FIAP.Tech.Challenge.Lambda/Services/CpfValidator.cs`;
- `src/FIAP.Tech.Challenge.API/Configurations/JwtSetup.cs`;
- controllers em `src/FIAP.Tech.Challenge.API/Controllers/Admin` e `Public`.

Observação: a chave JWT está hardcoded em `JwtSetup.cs` e também existe uma
chave padrão interna no serviço da Lambda. Isso reduz a segurança da entrega
quando os segredos não são sobrescritos por configuração externa.

1.3 Criar Function Serverless para validar CPF
Status: ATENDE

Existe uma AWS Lambda em C#/.NET no repositório separado. O handler suporta
AWS API Gateway HTTP API Payload v2.0, valida corpo vazio/JSON inválido/CPF
ausente e valida o CPF matematicamente antes de consultar o banco.

Evidências:
- `Function.cs`, método `ProcessarRequisicaoAsync`;
- `Services/CpfValidator.cs`;
- `infra/main.tf`, recurso `aws_lambda_function`.

1.4 Consultar existência e status do cliente
Status: PARCIAL

A Lambda consulta a tabela `"Clientes"` por CPF, com parâmetro SQL e retorno
404 quando não encontra o cliente. Porém a consulta seleciona apenas
`Id`, `Nome`, `Cpf`, `Email` e `Telefone`; não existe coluna de status no schema
entregue e o código define o status retornado como `"Ativo"`:

`ClienteDatabaseService.cs`:
`Status = "Ativo"`

Portanto a existência é verificada, mas o status real do cliente não é
consultado nem rejeitado quando inativo. Esse requisito deve ser considerado
incompleto.

1.5 Gerar e devolver JWT válido
Status: ATENDE PARCIALMENTE

`JwtTokenService.cs` gera token assinado com HMAC-SHA256, prazo configurável e
claims de identificação, CPF, e-mail, role Cliente e status. A API principal
valida a assinatura usando a mesma chave.

A classificação é parcial porque o Terraform da Lambda configura
`runtime = "dotnet8"`, embora o projeto seja .NET 10, e o Terraform utiliza
`dummy_payload.zip` como `filename`. A pipeline cria `lambda_payload.zip`, mas
esse arquivo não é referenciado pelo recurso `aws_lambda_function`. Assim, o
deploy descrito no código pode não publicar o binário produzido pela pipeline.

2.1 Quatro repositórios separados

2.2 CI/CD da Lambda
Status: PARCIAL

O workflow executa restore, build, testes, validação Terraform, build Docker e
um `terraform apply` na branch principal. Isso atende à estrutura de CI/CD.

A entrega não é considerada integralmente comprovada porque:
- não há evidência de uma execução bem-sucedida do workflow;
- o deploy pode usar o ZIP dummy apontado pelo Terraform;
- o runtime provisionado é `dotnet8`, divergente do .NET 10 documentado.

2.3 CI/CD da infraestrutura Kubernetes
Status: ATENDE PARCIALMENTE

O workflow executa `terraform fmt`, `init`, `validate`, `plan` em Pull Request
e `apply` em push para `main`/`master`. A estrutura de entrega automática está
presente.

Não há evidência versionada de execução bem-sucedida, de configuração de
credenciais AWS no ambiente real ou de que os recursos tenham sido
efetivamente provisionados.

2.4 CI/CD da infraestrutura do banco
Status: ATENDE PARCIALMENTE

O workflow executa validação Terraform, plan em Pull Request e apply na branch
principal. O repositório também contém DDL e seed versionados.

A classificação é parcial pela ausência de logs de execução/deploy e porque o
arquivo de exemplo define `multi_az = false`, contrariando a alta disponibilidade
descrita na documentação.

2.5 CI/CD da aplicação principal
Status: NÃO ATENDE INTEGRALMENTE

O workflow principal executa build, testes, build Docker e validação Terraform.
Entretanto, o job `deploy-kubernetes` não realiza conexão com um cluster nem
executa `kubectl apply`. O passo final apenas imprime mensagens como
"Executando Pipeline de Entrega Contínua" e "Deploy ... orquestrado com
sucesso".

Logo, existe pipeline de validação, mas o deploy automático da aplicação
principal não está implementado de fato.

2.6 Proteção de main/master e uso obrigatório de Pull Request
Status: NÃO COMPROVADO

Os READMEs dos quatro repositórios afirmam que as branches são protegidas e
exigem Pull Request. Contudo, proteção de branch é uma configuração do GitHub,
não um arquivo versionado, e não foi encontrada evidência verificável dessa
configuração na análise dos repositórios.

Os workflows são acionados por `push` e `pull_request`, mas isso sozinho não
impede commit direto na branch principal.

2.7 Deploy automático de homologação e produção
Status: NÃO ATENDE / NÃO COMPROVADO

Os workflows só contemplam `main` e `master`. Não foram encontradas branches ou
jobs específicos de homologação, ambientes separados ou estratégia de deploy
para homologação e produção. Há `environment = "production"` em exemplos
Terraform, mas isso não substitui uma pipeline de homologação.

10. CHECKLIST FINAL E AÇÕES RECOMENDADAS
=========================================

Para transformar a entrega em uma entrega comprovadamente completa:

1. Corrigir a Lambda para usar o runtime suportado pelo projeto .NET entregue,
   apontar o `aws_lambda_function.filename` para o ZIP gerado pela pipeline e
   garantir que o handler implantado seja o artefato publicado.
2. Implementar a consulta do status real do cliente ou remover a afirmação de
   que o status é consultado. O schema, SQL e código devem usar a mesma regra.
3. Completar o API Gateway central com as integrações e rotas reais para
   Lambda e aplicação no EKS.
4. Substituir o passo de deploy simulado do workflow principal por login no
   cluster e `kubectl apply -k k8s/`, ou por uma estratégia real equivalente.
5. Definir e documentar uma única política de HPA: máximo 5 ou máximo 10.
6. Habilitar Datadog no ambiente de entrega ou fornecer evidência de que ele
   foi habilitado, incluindo dashboards e monitores exportáveis.
7. Ativar Multi-AZ no RDS se a alta disponibilidade descrita for requisito da
   entrega, e alinhar o README, Terraform e variáveis de exemplo.
8. Implementar logging estruturado e correlação de requisições no código da
   API, não apenas no API Gateway/Datadog.
9. Criar monitores específicos para falhas de processamento de OS, além dos
   alarmes genéricos de latência e HTTP 5XX.
10. Adicionar links relativos válidos no README, removendo referências
    `file:///Users/...`.
11. Publicar o vídeo de até 15 minutos e incluir o link em um documento PDF
    único com os quatro repositórios e as documentações.
12. Anexar evidências administrativas da proteção de branches e da inclusão
    do usuário `soat-architecture`.

RESULTADO FINAL
==============

A solução apresenta uma base técnica consistente e documentada, mas a
classificação global é:

    ENTREGA PARCIALMENTE ATENDE AOS REQUISITOS DA FASE 3.

Os requisitos de arquitetura, organização dos repositórios, IaC, autenticação,
modelo de dados e documentação estão majoritariamente presentes. Os requisitos
de funcionamento comprovado em nuvem, deploy automático real, observabilidade
ativa, vídeo e entrega formal no Portal do Aluno permanecem incompletos ou não
comprovados no material analisado.
